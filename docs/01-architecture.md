# البنية المعمارية (Architecture)

## المبدأ الحاكم

> **المنصة نظام إدارة محتوى مصغَّر، لا موقع بمحتوى ثابت.**
> أي معلومة قد تتغير مستقبلاً تُحفظ في قاعدة البيانات وتُدار من لوحة الإدارة، لا في الكود.

## لماذا طبقة بيانات واحدة؟

كل استعلام يمر عبر `src/data/api.ts`. الفائدة العملية:

- **تبديل المزوّد لاحقاً** (Firebase أو خادم خاص) = تعديل ملف واحد، لا إعادة بناء.
- **رسائل خطأ عربية موحّدة** بدل رسائل تقنية إنجليزية متفرقة.
- **الأنواع مركزية** في `src/types/db.ts` ومطابقة للمخطط.

## المصادقة (Authentication)

- **الموقع العام:** بلا حساب. الزائر يقرأ المحتوى المنشور ويرسل الشكاوى فقط.
- **بوابة ولي الأمر:** بلا حساب أيضاً — تحقق من الهوية بكود الطالب والرقم القومي
  عبر دالة محكومة في قاعدة البيانات، مع تقييد المحاولات الفاشلة.
  (قرار متعمَّد: نظام حسابات كامل لأولياء الأمور يزيد التعقيد والتكلفة بلا حاجة في الإصدار الأول.)
- **لوحة الإدارة:** Supabase Auth (بريد وكلمة مرور) + وجود المستخدم مفعَّلاً في `admin_users`.
  التحقق يتم **داخل قاعدة البيانات** عبر دالة `is_admin()` في كل سياسة كتابة — لا في المتصفح.

## استراتيجية النشر

`main` على GitHub ← Cloudflare Pages (بناء تلقائي عند كل دفع) ← CDN عالمي.
متغيرات البيئة تُضبط في لوحة Cloudflare، ولا تُرفع مع الكود أبداً.

## الميزات المستقبلية

الأساس جاهز لها دون إعادة بناء:
- جدول `grades` قابل لإضافة مراحل جديدة (لا أرقام صفوف ثابتة في الكود).
- `audit_logs` جاهز لتسجيل العمليات.
- `attendance_records` يحمل الرصد اليومي التفصيلي (نظام حضور متقدم مستقبلاً).
- بنية `posts` بنوع `kind` تتسع لأنواع محتوى جديدة.
- الترجمة: كل النصوص الثابتة في مكونات محدودة، والمحتوى في قاعدة البيانات — إضافة الإنجليزية
  تعني إضافة أعمدة `*_en` وطبقة ترجمة، لا إعادة كتابة.
